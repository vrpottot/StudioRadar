# Хранилище StudioRadar

Приложение хранит рабочие данные в PostgreSQL проекта Supabase `mvjltbchktnqjhpddkju`.
Express подключается через `pg`; браузер обращается к Express. Supabase MCP нужен для администрирования, а не для запросов приложения.

| Таблица | Данные |
| --- | --- |
| `leads` | Каждый заказ отдельной строкой: ID, нормализованный уникальный URL, данные компании, контакты, задача, бюджет, цитаты, статусы, заметки |
| `pipelines` | Сохранённые стратегии поиска и их параметры |
| `app_settings` | Общие настройки без API-ключей; одна строка `global` |
| `search_runs` | Начало и конец запуска, результат, число добавленных лидов, диагностика, ошибки |
| `search_candidates` | Проверенные публикации, исходный текст, AI-решение и причина отклонения |

У лидов и пайплайнов есть `data JSONB`: исходные поля сохраняются без потери старых или дополнительных данных. Отдельные генерируемые столбцы используются для SQL-фильтров, ID и URL имеют ограничения уникальности. Изменения статуса и заметок сливаются на стороне PostgreSQL, без перезаписи всей базы.

## Подключение

В `backend/.env` нужен `DATABASE_URL`. Секреты не коммитятся и не передаются во frontend.
Для этого проекта создан отдельный серверный логин `studioradar_app`: он может работать только с пятью таблицами приложения. Он не администратор БД и не обходит RLS. Случайный пароль сохранён только в локальном `.env`; в истории миграции находится SCRAM-верификатор, а не исходный пароль.

Проверенное подключение: Session pooler `aws-0-eu-west-1.pooler.supabase.com:5432`, пользователь `studioradar_app.mvjltbchktnqjhpddkju`. Пароль находится только в `backend/.env`.

Публичный корневой сертификат Supabase включён в `backend/src/db/supabase-ca.crt`. Для адресов Supabase драйвер автоматически использует его с `sslmode=verify-full`, проверяя цепочку и hostname. Явно заданный `sslrootcert` сохраняется. Источник сертификата: [официальное хранилище Supabase](https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt); SHA-256: `807025ad50d4ed219d2c9c7d299c004f824eb00cf7f65afef607d07b72e6cafa`.

Для другого окружения возьмите строку подключения в Supabase Connect. При отсутствии IPv6 используйте session pooler. Используйте TLS с проверкой сертификата; при необходимости задайте доверенный сертификат Supabase через параметры PostgreSQL-клиента.

```bash
npm run db:check --prefix backend
npm test --prefix backend
```

Для нового проекта примените SQL-файлы по порядку. Первая миграция создаёт таблицы, индексы и включает RLS; вторая создаёт серверную роль и политики. Пароль этой роли задаётся отдельно. Не используйте строку с пользователем `postgres` в браузере.

## Перенос старого окружения

Сначала остановите процессы, которые пишут JSON, сделайте резервную копию и проверьте, что `DATABASE_URL` указывает на нужный проект.

```bash
npm run db:migrate-json --prefix backend -- --source-dir /path/to/legacy/backend --remove-files
```

Скрипт переносит все записи, в том числе скрытые текущей политикой, и проверяет точное совпадение данных в транзакции. Существующие отличающиеся записи не перезаписываются: миграция прервётся для ручного разрешения конфликта. Удаление файлов происходит только после commit, при условии что исходные файлы не изменились. Сохранённые API-ключи сначала нужно вынести в серверное окружение.

При деплое `scripts/deploy.sh` проверяет подключение заранее, сохраняет резервную копию старого приложения и переносит оставшиеся серверные JSON при остановленном сервисе. На VPS заранее должен быть настроен его собственный `backend/.env` с PostgreSQL `DATABASE_URL`: секреты из рабочего компьютера не входят в архив деплоя. Резервная копия приложения не заменяет резервную копию облачной БД.
