# StudioRadar AI — B2B Lead & Order Intelligence

Интеллектуальный радар и поисковик прямых коммерческих B2B-заказов для студий компьютерной графики, 3D/2D моушн-дизайна, CGI и видеопродакшна. Тендеры и фриланс-биржи исключены.

## Текущий поиск прямых заказов

Поиск через **оба Exa и Tavily** по публичным публикациям HH (включая региональные домены), Telegram, LinkedIn и Facebook. Закрытые группы и страницы за авторизацией не сканируются. Фриланс-биржи, тендеры, предложения исполнителей, новости о завершённых кампаниях и штатный найм исключены.

- Все 9 отраслей и 5 услуг из `ai/sources.js`; весь мир, включая Россию и СНГ. Страна заказчика должна подтверждаться цитатой. Каждый запуск охватывает все отрасли на каждой площадке; акцент услуги меняется ежедневно и между проходами, квалификатор проверяет полный список. Exa и Tavily получают разные формулировки, для LinkedIn/Facebook также используются англоязычные запросы.
- HH: явный запрос компании на студию/подрядчика для проекта. Удалённая вакансия или ГПХ сами по себе не подходят.
- Telegram: **явный бюджет проекта от 900 000 RUB**, подтверждённый точной цитатой. Бюджет «до», месячная зарплата, неизвестная сумма и другие валюты отклоняются до вызова Gemini. Автоматического пересчёта валют нет.
- Для остальных площадок минимальный бюджет не задан; неизвестный бюджет отображается как «Не указан».
- Нужны цитаты запроса, деятельности компании, страны и даты публикации; заказ должен быть открыт и опубликован за последние 90 дней. Имя автора не заменяет название компании, а покупка рекламного ролика не делает IT/BPO-компанию рекламным агентством.
- Кнопка поиска запускает до трёх проходов с целью 10 новых разных заказчиков. Один проход: 36 поисковых заданий (4 площадки × 9 отраслей), до 72 обращений к поисковым API, один вызов AI-планировщика, до 48 квалификаций и до 96 просмотров публикаций. Полный запуск ограничен 216 основными поисковыми вызовами и 144 квалификациями; дополнительные запросы профилей и повторы Gemini учитываются отдельно. Цель поиска не гарантирует результат: `target_reached` показывает, достигнуто ли количество без ослабления правил. Часовой мониторинг при активных пайплайнах сохраняет один проход с целью 3 заказчика.
- Gemini составляет до 12 новых формулировок для части отраслей/площадок на основе числовой сводки предыдущего прохода; охват всех девяти отраслей и четырёх площадок сохраняется. Если планировщик недоступен, используются подготовленные запросы. Модель планирует только запросы, а результаты поступают из Exa/Tavily.
- Генеративного резервного поиска без источников нет. Повторные URL не добавляются; при поиске LinkedIn один activity ID считается одной публикацией независимо от подписи URL и регионального домена. Старые записи остаются в БД при смене политики, но нецелевые источники скрываются из выдачи.
- Заглушки входа не затирают текст публикации из поисковой системы. API поиска возвращает `diagnostics`: число результатов, новых публикаций, проверок, причины отсева и ошибки источников. Одновременные запуски блокируются, чтобы не расходовать квоту повторно.
- Поисковые запросы используют явные формулировки заказчиков; публикации с признаками заказа получают приоритет перед наймом и рекламой исполнителей. Публичные Telegram-ленты используются для обнаружения отдельных постов (до 8 лент за проход); лента целиком не квалифицируется как заказ. Telegram-посты без нужного бюджета не расходуют лимит 48 AI-проверок.
- У LinkedIn извлекается текст и дата самого поста из JSON-LD, без комментариев и чужих предложений услуг. Для перспективных запросов проверяется точный профиль автора (до 12 профилей, до 36 дополнительных обращений Exa/Tavily вместе с Contents и резервным поиском). Из профиля можно подтвердить компанию и страну; запрос и дата должны подтверждаться самим постом. Совпадение имени с другим профилем не считается доказательством.
- При временных ошибках Gemini (408/429/500/502/503/504, сетевые сбои) запрос повторяется с увеличением паузы и случайной добавкой, максимум три попытки на модель. Учитываются `Retry-After` и Google RetryInfo; общий лимит вызова — 60 секунд. Затем используется резервная модель, если остаётся время. Ошибки ключа 400/401/403 не повторяются. Повторы расходуют квоту AI-провайдера.
- Подтверждённые заказы сохраняются сразу после проверки. Если последующий запрос Gemini завершится ошибкой, уже сохранённые записи останутся в БД, а история запуска и поле `partial_result` в ошибке API покажут их количество. Недоступность AI не считается отказом по критериям заказа.
- Все найденные публикации, включая ещё не проверенные, сохраняются в очереди `search_candidates` вместе с исходной датой. Следующий запуск продолжает очередь и добавляет новые результаты. Ошибки Gemini и ошибки сохранения лида оставляют запись для повторной обработки. Окончательная отметка принятия ставится после подтверждения записи лида в БД.
- Gemini получает JSON Schema для плана и квалификации; ответ проверяется локально. Обрыв `MAX_TOKENS`, повреждённый JSON и нарушение схемы не интерпретируются как «заказов нет».

Для работы нужны `EXA_API_KEY` и/или `TAVILY_API_KEY`, а также `GEMINI_API_KEY` в `backend/.env`. Используйте свои действующие ключи; в этот набор изменений ключи не включены.

Ручной поиск по умолчанию запрашивает до 10 заказов. Для поиска до 10 разных компаний: `npm run hunt:target --prefix backend -- --target 10 --rounds 3`. Команда делает максимум три прохода с разными формулировками, исключает уже проверенные URL и сохраняет подтверждённые заказы сразу в Supabase. Это цель поиска, а не гарантия количества: при нехватке подтверждений команда возвращает код 2, при ошибке API — код 1. Повреждённый JSON Gemini запрашивается повторно в пределах общего лимита; при явном исчерпании суточной квоты модель временно пропускается в текущем процессе, используется резервная.

```bash
npm test --prefix ai        # Офлайн-проверки, без расходов API
npm run build --prefix frontend
# Платный smoke-test по реальным источникам, только при настроенных ключах:
RUN_LIVE_HUNT=1 node ai/test_hunt.js
```

Если Gemini отвечает `API key not valid`, укажите действующий `GEMINI_API_KEY` в `backend/.env` и перезапустите backend. Ключи провайдеров хранятся только в окружении сервера. Рабочие ключи Exa/Tavily не заменяют AI-квалификатор; перед поиском его доступность проверяется через `POST /api/ai/check`.

## Архитектура проекта

```
studioradar/
├── frontend/   # React + Vite (интерфейс, дизайн-система, компоненты)
├── backend/    # Express API, PostgreSQL / Supabase, WebSocket, планировщик
├── ai/         # Автономный модуль поиска, парсинга и ИИ-квалификации заказов
├── docs/       # Техническое задание и документация
├── supabase/   # SQL-миграции и описание хранилища
├── .github/    # CI/CD автоматический деплой на VPS через GitHub Actions
├── .env.example # Переменные окружения без секретов
└── README.md
```

### Модуль `ai/` (Изолированный ИИ-движок)
Модуль инкапсулирует всю работу с нейросетями, поисковыми API и веб-скрапингом. Экспортирует единую функцию `huntOrders(options)`, которую вызывает бэкенд.

- `index.js` — главная точка входа, оркестрация поиска и экспорта `huntOrders()`.
- `search.js` — поиск по открытому вебу через Exa и Tavily Search API.
- `fetchPage.js` — загрузка веб-страниц, очистка разметки и извлечение текста через Cheerio.
- `classify.js` — фильтрация спама/резюме и нейросетевая квалификация («это заказ или нет»).
- `extractContacts.js` — парсинг и валидация телефонов, email, Telegram и должностей ЛПР.
- `sources.js` — реестр площадок, поисковых запросов и целевых направлений.
- `llm.js` — адаптер работы с Google Gemini API.

### Модуль `backend/` (Express API)
Бэкенд отвечает за REST API, хранение данных в БД, WebSocket-оповещения и расписание. **Бэкенд ничего не знает про Tavily и Gemini.**

- `src/config/` — конфигурация порта, CORS и загрузка окружения сервера.
- `src/db/` — подключение к PostgreSQL / Supabase, работа с лидами, пайплайнами, настройками и историей поиска. Локальных файлов с рабочими данными нет.
- `src/routes/` — маршруты API (`/api/leads`, `/api/stats`, `/api/ai`, `/api/pipelines`, `/api/signals`, `/api/settings`).
- `src/services/` — бизнес-логика (`leadService.js`, `pipelineService.js`, `hunterService.js`, `schedulerService.js`).
- `src/ws/` — WebSocket-сервер для моментальной передачи найденных заказов в интерфейс.
- `src/server.js` — запуск HTTP/WS сервера.

### Модуль `frontend/` (UI)
- Минималистичный интерфейс (Swiss / Nordic SaaS) без эмодзи.
- Таблица лидов с фильтрами, скорингом и быстрым вызовом звонка/Telegram.
- Экран аналитики спроса и 4 ключевые KPI-метрики.

## Быстрый старт

### 1. Установка зависимостей
```bash
npm install
cd backend && npm install
cd ../ai && npm install
cd ../frontend && npm install
```

### 2. Настройка переменных окружения
Скопируйте `.env.example` в `backend/.env` и укажите ключи:
```env
PORT=8001
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/postgres?sslmode=verify-full
GEMINI_API_KEY=your_gemini_key
TAVILY_API_KEY=your_tavily_key
```

Данные хранятся в таблицах Supabase `leads`, `pipelines`, `app_settings`, `search_runs`, `search_candidates`.
SQL-миграции находятся в `supabase/migrations/`; порядок настройки и перенос старых файлов описаны в [supabase/README.md](supabase/README.md).
Проверка подключения: `npm run db:check --prefix backend`. При недоступной БД сервер сообщает об ошибке и не подменяет данные пустыми файлами.

### 3. Запуск в режиме разработки
```bash
npm run dev
```
- Frontend: `http://localhost:5173`
- Backend API: `http://localhost:8001`
- WebSocket: `ws://localhost:8001`
